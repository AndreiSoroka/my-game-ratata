# Генерируемый Новогород и Колокол памяти

## Мир и воспроизведение

При запуске backend создаётся новая планировка Новогорода (`map-2-2`). Остальные
24 карты региона загружаются из существующих файлов без изменения геометрии.
`GAME_WORLD_SEED` фиксирует город и стартовый выбор состояния Колокола; без него
сервер выбирает случайный seed. Значение также записано в `generationSeed` карты.
Отдельные seed речи и предысторий NPC не заменяются seed города.

```sh
GAME_WORLD_SEED=novogorod-example bun run dev:backend
# Авторский экспорт только города и его старого файлового псевдонима:
GAME_WORLD_SEED=novogorod-example node scripts/generate-world.mjs --location map-2-2
```

Чистые `generateCity(seed, style?)` и `generateWorldMap(definition, options)` из
`scripts/generate-map.mjs` возвращают Tiled JSON и ничего не записывают. И сервер,
и файловый экспорт используют эти функции. Стиль — `grid`, `organic` или `ring`;
обычный запуск выбирает каждый с одинаковой вероятностью. Файловый экспорт —
отдельное авторское действие, он не выполняется при старте сервера.

Карты и разрешённые действия остаются разными слоями: сгенерированная геометрия
задаёт место, а общие сервисы `GameCharacter` проверяют движение, доступность,
бой, имущество и взаимодействия. Мир, договоры, городское состояние и личности
хранятся только в памяти процесса. Одинаковый seed не восстанавливает сохранение.

## Планировка и смысловые точки

Размер города — 96×80 клеток по 16 пикселей. Сохраняются одиннадцать зданий,
их размеры и интерьеры. Сначала резервируются укрепления и обязательные участки
часовни с кладбищем, тренировочного загона и площади 10×10. Дома размещаются до
рисования тайлов: до 32 попыток планировки и 128 кандидатов на участок; затем
используется проверенный шаблон выбранного стиля.

Между соседними домами и вдоль укреплений остаются две свободные клетки.
Крыши, фасады и декоративные объекты входят в проверку пересечений. Главные
дороги имеют ширину три клетки, подходы к дверям — две. Все входы, могильные
точки, тренировочный загон и четыре воротных прохода связаны проходимыми путями.

Крепостные углы — четыре отдельные башни 3×3. Одна функция строит все четыре
воротных узла: опоры 2×2, семиклеточный проём и по две открытые створки вдоль
стены. Центральная трёхклеточная дорога остаётся свободной. Направления и соседние
локации ворот берутся из определений региона. Укрепления не входят в слой
`Building covers` и не исчезают вместе с крышей ближайшего дома.

Стабильные ID и свойства карты служат единственным источником координат:

- `Buildings`: ID 100–110, `semanticId`, вход и место внутри здания.
- `City anchors`: `service.*`, `resource.*`, `spawn.grave-1`…`spawn.grave-6`,
  `player`, `bell` и `training`; прямоугольники `cemetery` и `plaza` имеют тип
  `city_area`.
- `Fortifications`: геометрия углов, опор, проёмов и открытых створок для проверок.
- `World interactions`, `Depth props` и ресурсные слои: существующие общие
  форматы взаимодействий, отрисовки, столкновений и добычи.

Жители начинают внутри своих помещений; Вера — внутри часовни. Обычное место
службы не является знанием текущего положения NPC, который уже ушёл оттуда.
Старые направления домов относительно площади не используются как постоянные
факты. Локальные тестовые карты могут передаваться напрямую как навигационные
фикстуры; без городских якорей сохраняется их прежний путь размещения.

## Загрузка карт клиентом

Протокол `0.10.0` передаёт `MapSummary.asset = { url, revision }` в `world_init`
и снимках локации. Backend отдаёт свою карту через
`/world/maps/:serverEpoch/:locationId.json`; старый epoch получает 404.
Версия содержимого используется как ETag, карта неизменна в пределах epoch.
Изображения и тайлсеты загружаются из статического `/game/map`.

Клиент сначала присоединяется к миру, затем загружает указанную сервером карту.
Новый epoch перезагружает даже прежнюю локацию. Поздний результат старой загрузки
не заменяет новый мир. При ошибке доступна кнопка **Повторить загрузку карты**.
Повторная загрузка не создаёт NPC, предметы, задания или новую награду.

## Общий городской заказ

Состояние Колокола хранится общим городским сервисом:

| Состояние  | Что происходит                                                   |
| ---------- | ---------------------------------------------------------------- |
| `silent`   | Колокол молчит; Капли ещё нет, можно взять городской заказ Миры. |
| `prepared` | Заказ исполнен; Колокол ждёт активации внутри часовни.           |
| `active`   | Городские услуги открыты, Капля существует.                      |

На старте Колокол с вероятностью 50% уже активен. В этой ветке сердца не нужны.
В другой ветке один общий заказ требует 3 настоящих сердца из инвентаря и имеет
один бюджет 40 золотых. Модель выбирает авторское предложение, а сервер задаёт
его требования и награду. Просмотр условий не принимает договор; распределение
награды фиксируется существующим выбором при принятии.

Первая успешная сдача атомарно расходует сердца, платит через общий сервис наград
и переводит Колокол в `prepared`. Конкурирующие принятые заявки получают
`cancelled` с причиной «городской заказ уже выполнен». Их владельцы не расходуют
вещи, не получают повторную выплату и не приобретают личное выполнение задания.

Подготовленный Колокол — обычный объект `bell` с ID `novogorod:memory-bell`.
Живой персонаж должен физически подойти к нему в часовне и выполнить
`world_interact`: сервер проверяет доступность, расстояние и видимость. Переход
в `active` один раз открывает услуги всем и регистрирует Каплю через общий путь
создания `GameCharacter`. Повторы команды и переподключения этого не дублируют.

До `active` закрыты покупка, продажа, ремонт, размещение и получение ремесленных
заказов, включая прямые команды и старые окна. Доступны разговоры, поручения,
помощь Веры, самостоятельное изготовление и обычная работа. Условия Новогорода
описаны данными `cityStoryDefinitions`; общий городской механизм не закрепляет
их за всеми будущими поселениями.

## Пробуждение и Вера

Новая личность появляется на свободной могильной земле у часовни, включая новую
жизнь после окончательной смерти. Переподключение сохраняет прежнюю позицию;
обычное воскрешение возвращает того же персонажа у его тела. Мирные надгробия
кладбища используют существующую графику и не являются источниками скелетов.
Лор объясняет новое пробуждение как Искру в оставленном теле; механика выбора
и захвата другого тела не добавлена.

Для пары Вера–новая личность один раз выбирается вариант знакомства. В половине
случаев в первой беседе звучит короткое вступление о пробуждении, городском порядке
и надежде на добровольную помощь; иначе эти темы остаются для вопросов. Текущие
факты важнее старого разговора: при `silent` Вера направляет к Мире, при
`prepared` — к Колоколу, при `active` знает о работающих услугах. Она по-прежнему
знает и преподаёт только молитвы Матери и Путника. Другие пробуждённые могут стать
товарищами по обычным правилам согласия; новые спутники автоматически не создаются.

Три PNG состояния и четыре кадра раскачивания Колокола имеют размер 48×64,
прозрачность и общую опорную точку. Исходный лист и промпт сохранены в
[`memory-bell`](../apps/frontend/public/game/assets/world/memory-bell/PROMPT.md).
Раскачивание запускается по серверному событию активации; снимки состояния
и повторное открытие карты не звонят заново.

## Проверки

`bun run check` запускает форматирование, типы, lint, unit/script tests и сборки.
Генератор проверяет по 100 seed каждого стиля, полную повторяемость карты,
проверенные шаблоны, геометрию и сохранность укреплений, отступы и достижимость.
Остальные 24 карты сравниваются с существующими определениями.

Браузерные сценарии выбираются по изменённому функционалу и работают headless:

```sh
node --test scripts/generate-city.test.mjs
bun run test:e2e -- e2e/city-fortifications.spec.ts
bun run test:e2e -- e2e/dynamic-map-loading.spec.ts
bun run test:e2e:graves
```

Проверки могил запускаются в отдельных свежих мирах для desktop/mobile. Полный
стандартный Chromium (`bun run test:e2e`) или `bun run check:full` вызывается
отдельно по явному запросу, а не перед каждым коммитом. Реальные модели не нужны
автоматическим проверкам; разговоры с моделью проверяются отдельно.

Ручная проверка настоящей моделью создаёт изолированные миры и не выполняет
решения. Каждый вопрос использует обычный сборщик контекста и общий предел
двух вызовов, включая поиск или исправление. Кейсы запускаются последовательно:

```sh
bun run npc:city:dialogue -- --list
bun run npc:city:dialogue -- --case=mira-silent
bun run npc:city:dialogue -- --case=vera-prepared
bun run npc:city:dialogue -- --case=vera-active
```

Проверяется объяснение общего заказа Миры и текущие сведения Веры до и после
активации, включая устаревший рассказ в памяти. Скрипт печатает реплики для
содержательной ручной оценки; настройки и полный модельный контекст не выводятся.
