# Repository Instructions

## Playwright

- Run Playwright tests and automation in headless mode by default.
- Use a visible browser only when the user explicitly asks to open, show, or visually inspect the UI in the in-app browser.
- The pre-commit hook uses `lint-staged` to check formatting and lint only staged files. Run `bun run check` separately for repository-wide formatting, types, lint, unit/script tests and builds. Browser E2E tests are manual.
- When gameplay or UI behavior changes, run the affected headless Chromium scenarios, for example `bun run test:e2e -- e2e/social-exchange.spec.ts`. Choose scenarios for the changed functionality; documentation or formatting changes do not require browser runs.
- The full standard headless Chromium suite remains available through `bun run test:e2e`. `bun run check:full` combines `bun run check` with that suite when explicitly requested. Firefox, WebKit, grave lifecycle and Storybook checks remain manual through `test:e2e:firefox`, `test:e2e:webkit`, `test:e2e:graves`, `test:e2e:storybook` or `test:e2e:all`. Do not add browser suites back to automatic checks without the user's request.

## Storybook

- For component stories in `Entities`, `Widgets` and `Shared`, use the layer and, where applicable, the slice or package as folders. The last segment of `title` matches the exact `.vue` filename without its extension, including capitalization. For example, use `Entities/Menu/MenuPanel`, `Widgets/Player vitals/PlayerVitalsWidget` and `Shared/Common/UiButton`. A gallery without a single component can use a descriptive title.
- Put state and example names such as `Normal`, `Disabled` and `AuthorizedNumbers` in story exports. When a title changes, update Storybook links and browser tests that use its story IDs.
- Storybook stories should showcase clean, focused components and states, not a one-off pile of unrelated UI inside every story.
- Extract reusable HTML/CSS/Vue primitives or render helpers first, then compose larger examples such as HUD groups, windows, inventory panels, or quest dialogs from those primitives.

## Shared game interface

- New vendor asset wrappers live in `apps/frontend/src/shared/ui/external/<pack>` with their assets, component-local stories/styles and per-component public APIs. Keep Shared independent of `game`; pass theme colors into external components. The independent Fantasy UI Borders component is documented in its module; legacy game controls migrate separately.
- New themed buttons use `UiButton` from `apps/frontend/src/shared/ui/common/button`. It composes the external borders and shared theme; keep its states and colors in that module instead of duplicating a button skin. The existing `GameButton` remains for unmigrated controls. Storybook groups these interface examples under `Shared`.
- Reusable rounded resource visuals use `BarTrack` and `GameBar` in `shared/ui/common`; pass fill/track colors from the shared theme. Game adapters own resource visibility and permitted precision.
- Composed presentation modules such as `apps/frontend/src/entities/menu` consume Shared through public APIs. The menu entity owns item navigation and focus through device-independent commands; input adapters map keys or gamepad input to those commands. Handle emitted action IDs, audio, modal ownership and server state in the game adapter.
- For controls without a Common replacement, use the production components in `apps/frontend/src/game/ui/primitives`: `GameButton`, `GameInput`, `GameSelect`, `GameTextarea`, `GameFrame`, `GameItemSlot`, `GameRibbon` and `GameResourceBar`. See that directory's `README.md` and the focused Storybook stories.
- Preserve intentional component skins. The game adapter positions the resources and effects widgets in one compact, lightly translucent dark green HUD frame with an inset beige Kenney border. It measures the frame height for neighboring overlays.
- Keep legacy colors, decorative asset sources and control states in `primitives/gameUi.css`; new Shared UI uses `shared/ui/theme` and its component styles. Parent styles own layout, sizing and scrolling, not a second button/field/frame skin. Preserve semantic resource colors and specialized world/SVG graphics.
- Keep native dialog surfaces and their DOM refs. Legacy frames use `GameFrame` as an aria-hidden decorative child of a `game-frame-host`; composed Common/Entities UI can use the external frames directly. Reuse `GameItemSlot` for item frames and interactive slots. Do not nest buttons or replace normal keyboard/command handling with presentation behavior.
- Cover new variants and visible states with the manual headless Storybook screenshot suite. Do not add browser suites to automatic checks or pre-commit.

## Shared character simulation

- Every playable character, scripted NPC, mob, or future model-controlled actor uses `GameCharacter` and the shared movement, combat, inventory, progression and resurrection rules. Controllers choose intentions; do not add a separate simulation for AI actors.
- Generated maps and initial story data are separate from authoritative game rules. The current region is the 5×5 Lands of Novogorod: 25 locations, with the city at `CENTER_LOCATION_ID` (`map-2-2`). Consume `GRID_SIZE` and `WORLD_LOCATION_DEFINITIONS` from `contracts/src/world.ts`; do not duplicate the grid or location names in clients, generators or spawn rules.

## Agent playtesting

- Use the connected Playwright/browser MCP with `http://localhost:4173/?test=1` when the local preview is running. The opt-in `window.__ratataTest` interface supports `join`, `observe`, `navigate`, `travel`, `act`, `waitFor`, `getState`, `moveFor`, `send`, `inventory` and `stop`. See `docs/agent-playtesting.md` for the AI workflow and result semantics; receiving a newer snapshot does not by itself prove an action succeeded.
- All test actions go through ordinary validated player commands. Avoid teleporting or editing live character state to claim a gameplay check passed.
- See `docs/playable-world.md` for startup commands, controls, generated-world content and runtime limitations. Keep playtesting headless unless the user asks to see the browser.

## Architecture decisions (Excalibur review, 2026-11-06)

These are project rules derived from our multiplayer RPG, not a requirement to rewrite working modules all at once. The installed engine is **Excalibur 0.32.0**. Check its local TypeScript declarations before copying examples from newer documentation. In this version `System.priority` is **static**, update runs before draw, and lower priorities run earlier.

### One character model, composed capabilities

- Keep `GameCharacter` as the shared authoritative character model. Humans, model agents, scripted residents, companions and hostile creatures use the same movement, combat, resources, skill practice and life-cycle services. Avoid separate player/NPC simulations or a deep subclass tree for every species, class and controller combination.
- Compose capabilities as typed state and shared systems/services: identity, location, health/life, movement, equipment, skills, faith, speech, personality and party membership. The controller submits intentions; the simulation validates and resolves them. Existing services already follow this separation; extract a component/system when it removes actual duplication.
- Species, visual appearance, faction, speech capability and personality remain separate data. Spark means an active human connection or accepted model-control lease; purely scripted actors and disconnected humans are Echoes. A slime can speak if its profile permits it; Spark/model control alone does not grant speech, combat ability, consent or ownership. Immutable human ownership remains protected even while that disconnected character continues a scenario as a visible, vulnerable Echo.
- Starting classes are backgrounds, not permanent learning restrictions. Practice comes from validated meaningful actions, not repeated empty commands or UI counters. Learning, teaching, miracles and multiclass costs use the same rules for every actor.

### Authority, commands and events

- `contracts` contains serializable messages and snapshots without Vue, Excalibur or server objects. Parse untrusted input at the boundary. The server resolves the actor from the connection/authorized agent session, never from a client-supplied owner ID.
- Server simulation owns position, collision, reach, line of sight, mana, cooldowns, damage, loot, trades, party consent, quest credit, faith and permanent death. Excalibur actors are views of snapshots. Client animation, collision callbacks or AI prose must never grant rewards or decide damage.
- Apply changes as commands -> shared rules -> typed domain events -> snapshots. Emit death, reward, trade and quest completion once per resolved action; use stable receipt/event identities where retry or replay is possible. Check costs, capacity, participation, proximity and resulting state as one operation.
- Theft transfers a real unequipped inventory instance atomically, using the shared service for player and agent commands. Reject invalid/empty attempts before costs or practice; impose actor and target-pair cooldowns. Keep undetected outcomes, exact practice counters and private bag contents out of other players’ events/snapshots; public attained abilities must not expose pending practice. NPC pocket contents are finite authored world data, never freshly minted theft rewards. Crime reactions use ordinary navigation/combat and personal hostility; never commandeer a human-controlled victim or accept an unproven guard accusation. Distinguish urgent guard calls from formal city reports. A valid city record follows the living identity through logout/travel/resurrection and blocks purchases on the server; permanent death creates a fresh identity. Absolution validates authority, reach and balance before an atomic payment, consumes old evidence and revokes related pursuit/attack rights. Never allow an old report or stale shop window to bypass these transitions.
- Keep simulation order explicit: controller intentions, movement/travel, combat resolution, life-cycle, shared objective updates, snapshots. Pass time and randomness into rule functions where practical. Tests must cover cooldown boundaries, failed miracles and repeated reward requests without wall-clock sleeps.
- All combat controllers use the same reach geometry as hit resolution. Never make AI stop at an unrelated hard-coded radius. Movement paths and map collision agree on world pixels, tile coordinates and the actor footprint; convert units explicitly.
- Keep clocks separate: authoritative server deadlines remain server-owned even when a client tab is hidden. Rendering time and frame interpolation cannot extend a resurrection window or affect practice rewards. Excalibur `fixedUpdateFps` is not network-snapshot interpolation; use it only for client systems that actually need a fixed simulation step.

### Excalibur presentation systems

- Prefer data components plus cached ECS queries for repeated visual behavior (snapshot binding, nameplates, selection, interpolation, status effects). Create queries once per scene/system, not once per actor per frame. Keep a stable server-character-ID to rendered-entity mapping.
- Declare system phase/priority deliberately. Snapshot reconciliation precedes presentation interpolation and animation; drawing must not mutate authoritative state. Use built-in Transform/Graphics components before adding an equivalent custom mechanism.
- Hit feedback consumes authoritative resolved damage events even when their numeric amount is hidden, survives attack-animation updates briefly, and yields to death. Use bounded scene-clock effects and per-actor graphics/actions; do not tint cached sprite assets shared by several characters. Sort building covers at their authored front ground line so outside characters are not hidden by a facade. Combat numbers are projected per observer on the server; never recover foreign HP or damage from internal simulation state. Training targets use the same combat rules and measure impact without HP loss, practice or rewards; their special targetability must not change faction hostility. Geometric combat guides are clipped to map-authored training interiors.
- Scenes own rendered map content, transient actors, visual timers, subscriptions and effects. Changing or unloading a scene must dispose them, cancel obsolete asynchronous loads and retain the server character identity, inventory, quests and party.
- Use Actions for cosmetic sequences and ParticleEmitter for spell/miracle feedback, with bounded lifetimes and counts. A visual fireball does not apply damage. Use Excalibur Timer/Clock scheduling for effects that must pause with the scene; UI timers may use browser timers when they are cleaned up on teardown.
- Nearby interactions must work without a mouse: Q selects self; E cycles nearby visible characters and interactive objects from nearest to farthest, Shift+E reverses; F uses the selected target or one visible target in the facing direction, performs its sole action directly or opens only that target’s choices; arrows or W/S move menu selection, F or Enter/Space activates and Esc returns focus. Ignore held confirmation repeats; the key that opens a menu must not also activate its first item. Escape must still close the owning window after a background click moves focus, without closing a different active dialog. The world highlight consumes that exact UI-selected target; do not run an independent nearest-target selector or mutate shared sprite materials for selection. Keep an open interaction menu pinned to the same target and semantic commands; disappearing, hidden or unreachable targets close it rather than substituting a neighbor. Clear held movement when opening a menu, consume game input while it owns focus and revalidate target reach/life/location before acting. Use physical key codes for WASD shortcuts so keyboard layout does not change movement.
- Ground audio consumes authored surface metadata. Every walking actor uses the same cadence/attenuation rules; validate actual displacement and cap voice counts. Per-source gain must not mutate other playing voices. Map changes, hidden pages and runtime disposal clear movement audio.
- Stealth and dash are authoritative movement intentions shared by all controllers. Emit hearing signals only from real collision-resolved displacement, with authored surface and gait loudness; never accept client noise or speed. Heard noises and ally alerts contain last-known positions with bounded lifetime, not an unseen target's live coordinates.
- Terrain stays on the ground layer. Trees and tall props are complete Y-sorted objects with an explicit ground-contact baseY; map clearing and furniture placement operate on whole footprints. Keep interactive sign/barrel/water metadata independent of atlas GIDs and validate server reach and line of sight. Shared containers grant their contents once per world session.
- Materials are normal inventory instances, never a parallel unlimited wallet. Inventory capacity counts occupied slots; herb and grain stacks cap at nine while other current items cap at one. Shared add/transfer rules merge only compatible stackable item IDs and preserve quantities atomically; gathering and crafting validate the resulting bag before spending ingredients, energy or a shared world source. Derived material totals are snapshot views of the actual bag. Opening a chest inspects a shared container; it does not spawn loot. Send its contents only to a validated nearby viewer. Individual and bulk transfers move existing item instances atomically, keep overflow in the container and recheck capacity, reach, line of sight and actor availability. Attacking spills only the remainder. Closing, travel, disconnect, death and lost reach revoke the inspection session; client windows never own inventory mutations.
- Give transient action results stable per-identity receipts that change on new outcomes, including repeated equal text, never on snapshot reads. Render one expiring notification channel; do not let persistent snapshot strings or reopening windows resurrect an expired toast. Keep lasting quest/inventory/party facts in their normal panels.
- Vue owns accessible menus, text entry, inventories, dialogue, knowledge and party UI. Canvas owns world-space rendering. Focused text/buttons must not leak movement/attack inputs; blur, death, disconnect and unmount release held controls.
- Debug collision zones, paths and entity IDs in opt-in test/debug mode. Test visual timing with Excalibur's TestClock where appropriate; keep domain-rule tests headless and independent of WebGL.

### Generated world, NPC reasoning and future cities

- Generated content is validated data with stable IDs, version, seed and references: locations, adjacency, NPC profiles, dialogue facts, quest objectives, rewards and merchant offers. Never execute model-generated code or treat dialogue/lore as developer instructions.
- Generation and model calls run outside the simulation tick. A bounded controller/decision adapter translates output into ordinary intentions, validates it, and falls back to local behavior on timeout. Keep command leases, cancellation and dialogue history scoped to the correct living identity. Do not claim a live language model is connected when the policy is scripted.
- NPC follow, guard, fight and flee are controller policies over shared navigation/combat. Check consent, speech, personality and current ownership. Crossing a location uses ordinary travel, including companions; do not teleport them to make tests pass.
- The current 5×5 grid is a region configuration, not a permanent world-size rule. Danger is authored world data (currently Manhattan distance from Novogorod, 0–4); the central city has no hostile spawns and outer encounters scale in count and strength. Generated buildings, enterable interiors, doors, furniture and collision footprints must agree. Roof covers are presentation only. Roads, service NPCs, farm beds, resource deposits and all four travel edges must remain reachable. New systems must consume location IDs/adjacency and dimensions from world data. Guilds are one source of adventures; individual NPCs can also give quests. Future cities, local inventories/prices and trade routes belong to location/content data, not hard-coded city branches in character logic.
- Every outdoor profession must use the shared worker-request service: retain its worksite and observed threat, physically report to the settlement clerk, wait for a claimed request, and verify recovery with one ordinary work action and a return trip. Work blocking belongs to the authoritative command boundary, independent of controller ownership. One real trophy is consumed per incident; retries never consume it again. Revalidate worksite danger before atomically paying and releasing the worker. New professions supply a work target and work-step adapter, not a separate quest or movement simulation.
- All gold-reward quests use the shared atomic payout service. Choose submitter-only or equal current-party distribution at acceptance and keep it fixed. Treat the displayed reward as one total budget; determine recipients from server membership at turn-in, conserve integer gold and retain stable per-instance payout receipts. Receiving a share must not complete the recipient's own quest.
- Shared farm plots are world state, not per-player rewards or client countdowns. Server time, proximity, costs and harvest phase are checked atomically; repeated or simultaneous harvests grant grain once.
- Persist world state separately from Excalibur entities: versioned plain data, stable character identity, quest/reward receipts and explicit migrations. Save actual resolved outcomes, not only an RNG seed. Current storage is in-memory; never describe it as durable persistence until save/load is implemented and tested.
- Entity existence and observation are distinct. Send only the relevant location/interest area and the perception the character has earned (including divine mood). Loading a map must not regenerate personal quests, recreate dead identities or repay completed contracts.

### Adoption and verification

- Prefer the current map loader until a concrete feature needs the official Tiled plugin; if adopted, verify Tiled properties/solids against the server navigation grid and retain strict parsing. Pin compatible versions; adding a plugin is not itself a reason to replace working code.
- Measure before adding spatial indices, chunk streaming, pooling or a new ECS package. Useful metrics are server tick time, active actors/particles, navigation work and snapshot size. Cache/filter by location first; never sacrifice authoritative rules to hide a performance problem.
- For behavior changes, test the failure and exploit cases as well as the happy path: disconnected/dead actors, cross-location targets, consent, stale invitations, double rewards, RNG outcomes and new identity after death. For UI changes, use the ordinary command interface and inspect the browser at desktop/mobile sizes.
- The browser test interface controls a player through the normal socket. `scripts/agent-mcp.mjs` exposes `ratata_observe` and `ratata_act` for NPCs through an optional token-protected local bridge; it is a controller port, not a state editor. Do not expose tokens in logs, client bundles or generated content.

### Dependency compatibility after the 2026-11-06 upgrade

- Use Bun 1.4.4 and the committed `bun.lock`; all workspace dependencies were checked against stable registry tags. Excalibur 0.32.0 is still the latest stable release. Do not replace a stable engine with the `next` alpha tag as an incidental dependency update.
- TypeScript 7 provides the `tsc` CLI through `@typescript/native` (an alias of `typescript`). ESLint and `vue-tsc` still need the TypeScript 6 JavaScript API, so the `typescript` dependency in root/frontend aliases `@typescript/typescript6`. Keep these separate; replacing the compatibility alias with TS7 breaks the tools. Follow Microsoft's [side-by-side migration](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-6.0).
- `baseUrl` was removed in TS7. Keep `paths` targets explicitly relative to their configuration file; do not restore deprecated flags to hide migration errors.
