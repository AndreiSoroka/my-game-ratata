# Знания мира

Этот корпус — общий источник описаний действующих игровых возможностей для
разговоров NPC и проверки функционала при разработке. Статьи написаны по-русски,
языком обитателя мира. Они объясняют, что можно сделать, что потребуется и какой
результат ожидать. Корпус не предоставляет способности и не заменяет авторитетные
игровые правила.

Папки обозначают **тему**, метаданные — **доступ**. Единственный авторский
источник метаданных — [catalog.json](catalog.json): его редактируют вручную.
Markdown-файлы содержат только заголовок и внутриигровой текст, без frontmatter.
Перемещение статьи требует изменить её путь в каталоге и не меняет доступ.
`README.md` служит разработчикам и не попадает в поиск.
Пользовательское управление описано в [гайде](../docs/playable-world.md), а
устройство NPC и RAG — в [техническом руководстве](../docs/npc-ai.md).

## Общие сведения и профессиональные подробности

Общая статья содержит полезное объяснение без необязательных чисел. Например,
[рубка деревьев](forestry/chopping.md) доступна всем, а её
[профессиональное дополнение](forestry/chopping-expert.md) — дровосекам. В нём
указаны точные выходы, затраты и различия деревьев. Общий текст в дополнении
повторять не нужно; связь указывает `extends`.

Обычный житель может объяснить рубку и посоветовать инструмент, не выдумывая выход
древесины. Дровосек знает точные действующие величины. Услышанные в разговоре
подробности могут остаться в личной памяти другого персонажа как сведения от
рассказчика; запретов пересказа сейчас нет.

## Каталог и текст статьи

Все метаданные находятся в `catalog.json`. Версия схемы обязательна; каждый
элемент связывает стабильный ID с одним Markdown-файлом:

```json
{
    "schemaVersion": 1,
    "articles": [
        {
            "id": "forestry.chopping.expert",
            "file": "forestry/chopping-expert.md",
            "audiences": ["profession:lumberjack"],
            "aliases": ["сколько древесины", "выход дерева"],
            "extends": "forestry.chopping",
            "sources": ["apps/backend/src/game/harvestRules.ts"],
            "checks": ["apps/backend/tests/harvesting.test.ts"],
            "facts": { "forestry.adult.wood": 8 }
        }
    ]
}
```

В самой статье остаются заголовок первого уровня и короткий самостоятельный
текст. Название извлекается из заголовка, его не нужно повторять в JSON. Путь
`file` задаётся относительно папки `knowledge`; ID, путь и непустой `audiences`
обязательны. Каталог задаёт порядок статей. Повторные пути, пропавшие и неучтённые
Markdown-статьи, выходы за папку через путь или символическую ссылку запрещены.

Каждая статья корпуса также указывает непустые `sources` и `checks`: существующие
пути от корня репозитория к реализации и проверяющим сценариям. `facts` содержит
проверяемые численные утверждения из реестра, основанного на действующих игровых
данных и функциях. Указанные числа должны присутствовать и в тексте; длительности
можно описывать естественными секундами или минутами.

`aliases` добавляет поисковые формулировки, но не дополнительные правила.
`extends` ссылается на существующую общую статью. Источники, проверки и численные
утверждения служат разработчикам и не добавляются к словам NPC. Не помещайте
служебные заметки в тело статьи.

Ориентир для автора — несколько коротких абзацев. Важен весь вход эмбеддинга:
заголовок, текст, поисковые названия и префикс модели должны укладываться в
фактический лимит 384 токена. Реальная проверка токенизатором выполняется через
`bun run knowledge:smoke` после подготовки локальной модели. Длинную статью нужно
разделить по смыслу, а не обрезать в середине условия.

## Аудитории

Внешний список означает **ИЛИ**. Вложенный список означает **И**:

```json
{
    "audiences": [
        "character:npc_magic_slime_1",
        ["profession:lumberjack", "resident:map-2-2"]
    ]
}
```

| Атом                          | Основание доступа                                  |
| ----------------------------- | -------------------------------------------------- |
| `common`                      | Общее знание всех персонажей                       |
| `creature:humanoid`           | Авторитетный тип существа из контрактов            |
| `archetype:slime`             | Авторитетный архетип                               |
| `profession:lumberjack`       | Реальная профессия или авторский профиль           |
| `doctrine:prayer`             | Религиозное учение; аналогично `doctrine:magic`    |
| `resident:map-2-2`            | Явная принадлежность к поселению, не его посещение |
| `character:npc_magic_slime_1` | Конкретная стабильная идентичность                 |
| `knows:pray`                  | Действительно изученное действие                   |

Используются только известные серверному реестру значения. Пустой список,
неизвестная аудитория, повторный ID и сломанная ссылка считаются ошибками. Не
задавайте доступ именем файла, никнеймом, внешностью, наличием Искры или видом
контроллера. Стартовое призвание не служит вечным ограничением обучения.

Личные документы содержат только реальные авторские сведения о конкретном NPC.
Полученные во время игры истории остаются в личной памяти, а не записываются в
общий корпус. Неизвестные личные звёзды не описываются как доступные знания:
персонаж получает только собственные открытые подробности через существующую
проекцию.

## Что откуда берётся

В статьях находятся устойчивые правила и известные обычаи: инструмент для рубки,
способ ремонта, обычное дело мастера, условия помощи павшему. Точные текущие цены,
остатки, готовность заказа, принятые договоры, состояние грядки, невидимое положение
персонажа и настроение бога сюда не переносятся. Для них нужны разрешённые текущие
наблюдения и личная память.

Имена и география земель, ориентиры, обычный ассортимент мастерских и известные
звёзды продолжают опираться на существующие структурированные игровые данные. При
изменении состава услуг нужно сверять местную статью с этими определениями.

В тексте NPC нет клавиш, кнопок, интерфейсных панелей, браузера, протоколов,
идентификаторов команд, серверных снимков и инструкций разработчику. Это содержание
пользовательского или технического руководства. Планы будущих возможностей не
представляются как уже доступные действия.

## Загрузка и сборка

При разработке backend один раз читает авторский каталог и перечисленные тексты.
Во время сборки структура, доступы, ссылки и факты проверяются, затем создаётся
один серверный артефакт `dist/backend/knowledge.json`. Его не редактируют вручную:
это результат сборки, а не второй авторский каталог. В производственном запуске
backend один раз читает этот артефакт; исходные Markdown и каталог ему не нужны.
Старый каталог статей в `dist/backend/knowledge/` при сборке удаляется.

Вся база остаётся на backend. Модель не получает пути, аудитории и технические
ссылки; доступ к найденным сведениям сервер проверяет для настоящего персонажа.

## Когда NPC обращается к знаниям

Первый вызов модели получает разговор, наблюдения и краткую сводку разрешённых
тем и специализаций. Статьи заранее не подмешиваются. Если сведений недостаточно,
NPC возвращает `informationRequest` с типом `knowledge_search` и собственным
поисковым запросом. Сервер ищет от имени этого персонажа и передаёт результат
второму вызову модели. Приветствие, благодарность или уже известный факт могут
обойтись без поиска; знак вопроса ничего не переключает.

Это инструмент существующего JSON-протокола NPC. Один вход допускает один запрос
информации — поиск знаний либо глубокую личную память — и максимум два вызова
модели с общим тайм-аутом и бюджетом.

## Кеш векторов

Векторы устойчивых статей и авторских справочников автоматически сохраняются в
`.cache/ratata-knowledge/vectors.json`. После перезапуска неизменившийся текст,
включая поисковые названия, использует готовый вектор. Смена модели или её
параметров делает прежние записи несовместимыми. Метаданные доступа продолжают
проверяться при каждом поиске независимо от кеша.

Кеш содержит хеши и векторы. Переписка, запросы игроков и личные открытия звёзд в
нём не сохраняются. Вектор нового запроса вычисляется при поиске. Повреждённый
или недоступный кеш не должен останавливать работу: отсутствующие векторы можно
построить заново, а лексический поиск остаётся доступным. Файл кеша не входит в
репозиторий и не является сохранением мира.

## Изменение правил

Сначала найдите действующее правило и его проверку. При намеренном изменении
поведения обновите реализацию, соответствующие статьи и тесты вместе. При переносе
старой документации не меняйте игру, чтобы подогнать её под устаревший абзац.

Проверка корпуса и фактов не загружает модель и не вызывает платные API. Проверки
реальных эмбеддингов и разговоров выполняются отдельно. Короткие статьи передаются
в контекст целиком; доступ проверяется до поиска и повторно после его завершения.

Команды проверки:

- `bun run knowledge:check` — структура, ссылки и соответствие численных утверждений игровым правилам; также выполняется при сборке backend.
- `bun run knowledge:smoke` — токены всех статей и поиск настоящими локальными эмбеддингами, включая доступ и релевантность выдачи Миры, Веры, Капли и Данилы; нужна заранее подготовленная модель.
- `bun run knowledge:dialogue` — ручной прогон шести сценариев настроенной модели NPC: благодарность без поиска, просьба указать кузнеца без вопросительного знака, объяснение рубки, незнакомые количества, знания дровосека и наличие у Игната. Модель сама выбирает поиск: первый вызов получает контекст без статей, при запросе информации второй — разрешённые результаты. Выполняет реальные вызовы модели в отдельном мире, игровые действия не применяет.
